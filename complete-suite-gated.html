Module 01

GitHub + Netlify: Free Hosting Setup

Before writing a single line of your website, you need a place to store your files and a way to publish them automatically. This module covers GitHub (where your code lives) and Netlify (what serves it to the public) - two free tools that together replace what used to cost hundreds of dollars a month in hosting.

What is GitHub, and why is it not optional?

GitHub is version-controlled cloud storage for code. Think of it like Google Drive for your website files, but with a superpower: it remembers every change you've ever made. Every time you update your website, you save a labeled snapshot. If you accidentally break something, you can roll back to any previous version instantly.

The other reason GitHub matters: Netlify (your hosting platform) watches your GitHub repository and automatically re-publishes your website every time you push a change. No FTP clients, no manual file uploads, no logging into a server. Push code → website updates. That's the whole workflow.

GitHub vs. just emailing yourself files: You could technically save your website files in a folder on your computer and upload them manually to any host. But the moment you want automation, database integration, serverless functions, or SSL certificates, you need a proper deployment pipeline. GitHub + Netlify is the industry standard for exactly this - and it's free.
Creating your GitHub repository

A repository (usually called a "repo") is a project folder on GitHub that tracks every version of your files.

Go to github.com and create a free account. Use an email you check regularly - GitHub sends security alerts there.
Click the green "New" button on your dashboard. Name the repository after your business using lowercase letters and hyphens only - no spaces, no capitals. Example: hartley-cleaning-co or my-business-site.
Set it to Public. Netlify's free tier connects to public repos without issue. Private repos require a paid GitHub plan or paid Netlify plan.
Check "Add a README file" - this creates the repo with an initial file so it isn't empty. Click "Create repository."
Common Issues
"Repository name already exists"
The name is taken in your account. Add a year or distinguishing word: my-business-site-2024. Repository names only need to be unique within your own account, not globally.
Not sure whether to make it public or private
Make it public. Your code is available to anyone who looks for it, but nothing about your database passwords or secret keys should ever be committed to GitHub (we cover this in Module 3). Public code with secrets in environment variables is standard practice and completely safe when done correctly.
Installing Git on your computer

Git is the underlying software that tracks changes and connects your computer to GitHub. It's different from GitHub - Git is the tool, GitHub is the cloud service that hosts what Git manages.

Mac: Open Terminal (search "Terminal" in Spotlight). Type git --version and press Enter. If Git isn't installed, macOS will ask if you want to install developer tools. Click Install. It takes about 5 minutes.
Windows: Download Git from git-scm.com. Run the installer - the default options are all fine. When it asks about your default editor, choose VS Code if you have it, or Notepad as a fallback.
After installing, configure your identity. Open Terminal (Mac) or Git Bash (Windows) and run these two commands:
git config --global user.name "Your Full Name" git config --global user.email "you@youremail.com"
Use the same email as your GitHub account. This info gets attached to every save (commit) you make.
Download your repository to your computer. In Terminal, navigate to where you want your project folder to live (e.g., your Desktop or Documents), then run:
git clone https://github.com/YourUsername/your-repo-name.git
Replace YourUsername and your-repo-name with your actual GitHub username and repo name. This creates a local folder connected to your GitHub repo.
Common Issues
"git: command not found" after installing
On Mac, you may need to close Terminal completely and reopen it. On Windows, make sure you're using Git Bash (installed with Git), not the default Windows Command Prompt.
Git asks for username and password when cloning
GitHub no longer accepts passwords - it uses Personal Access Tokens. Go to GitHub → Settings → Developer Settings → Personal Access Tokens → Tokens (classic) → Generate new token. Give it "repo" scope. Copy the token and use it as your password when prompted. You'll only need to do this once if you save credentials.
"Permission denied (publickey)"
This means GitHub doesn't recognize your computer. The fix is to set up SSH authentication. Run ssh-keygen -t ed25519 -C "you@email.com" in Terminal, press Enter through all prompts, then run cat ~/.ssh/id_ed25519.pub and copy the output. Go to GitHub → Settings → SSH Keys → New SSH Key, paste it in. Then clone using the SSH URL (git@github.com:username/repo.git) instead of HTTPS.
AI tip for Terminal errors: Git error messages are notoriously cryptic. If you get any error during setup, copy the entire error message and paste it to Claude with the message: "I'm setting up Git for the first time. Here's the error I got: [paste error]. What does this mean and how do I fix it?" You'll get a plain-English explanation and exact steps to fix it within seconds.
Connecting to Netlify

Netlify is your hosting platform. When you push code to GitHub, Netlify picks it up automatically and re-publishes your website. The free tier includes enough bandwidth and builds for any small business site.

Go to netlify.com and click "Sign up." Choose "Sign up with GitHub" - this links your accounts so Netlify can access your repositories without any additional configuration.
Click "Add new site" → "Import an existing project" → "GitHub." Netlify will ask permission to read your repositories - approve it.
Select your repository. On the build settings screen, leave everything blank. Plain HTML/CSS/JS websites don't need a build command. Click "Deploy site."
Netlify will deploy in 30-60 seconds and give you a randomly generated URL like lucky-cake-4b2d91.netlify.app. Your website is live. You'll connect your real domain in Module 10.
Build minutes: Netlify's free plan includes 300 build minutes per month. Each time you push to GitHub, Netlify uses a small amount of build time. If you're constantly pushing tiny changes, you'll drain your build budget. Get into the habit of grouping your edits and pushing once, rather than pushing after every line change.
Common Issues
Netlify deploys successfully but the site shows a blank page
This almost always means your main HTML file isn't named index.html. Netlify (and all web servers) look for index.html as the default page. Rename your main file and push again.
Netlify says "Repository not found" when linking
Go to Netlify → Team settings → GitHub access → Configure. Make sure Netlify has access to your specific repository. By default, GitHub only grants access to repositories you explicitly select.
I pushed a change but the site didn't update
Check the Netlify dashboard for your site - click "Deploys." You'll see a list of all deployments. If the latest one shows "Failed," click it to see the error log. If it shows "Skipped," Netlify may have rate-limited your builds due to too many rapid pushes.
Your daily Git workflow

Every time you make changes to your website, you follow the same three steps to save and publish them. This becomes automatic after a few days.

# Step 1: Stage the file(s) you changed # Use the exact filename, or "." to stage everything git add index.html # or git add . # Step 2: Commit - create a labeled snapshot of your changes git commit -m "Update pricing section with new rates" # Step 3: Push - send to GitHub, which triggers Netlify to redeploy git push
Write useful commit messages. "Update" or "Fix" tells you nothing in 6 months. Write what changed and why: "Fix mobile layout on services section" or "Add FAQ section with 7 questions." Future you will be grateful.
Common Issues
"Nothing to commit, working tree clean"
Git doesn't detect any unsaved file changes. Make sure you actually saved the file in your text editor (Cmd+S / Ctrl+S) before running git add.
"error: failed to push some refs" or "Updates were rejected"
Your local copy is behind the remote. Someone (or you on another machine) pushed changes you don't have yet. Run git pull first, then git push. If git pull creates a merge conflict, AI can walk you through resolving it - just paste the conflict output.
I accidentally committed a password or secret key
This is serious. First, immediately revoke and regenerate the key you exposed (do this in Stripe, Supabase, or wherever it came from). Then remove it from your code, commit, and push. The key will still be visible in Git history - if the repo is public, consider the key permanently compromised and treat regeneration as mandatory, not optional.
The netlify.toml configuration file

This optional file lives at the root of your project and tells Netlify how to handle your site - redirects, security headers, function settings, and environment rules. You create it once and it applies on every deploy. Having it from the start saves headaches later.

# netlify.toml - place this in your project root folder [functions] node_bundler = "nft" # Required if you use Netlify Functions (Module 6) [[redirects]] from = "/book" to = "/#booking-form" status = 302 # Temporary redirect (use 301 for permanent) [[headers]] for = "/*" [headers.values] X-Frame-Options = "DENY" X-Content-Type-Options = "nosniff"
You won't need this file immediately, but create it early. When you add Netlify Functions in Module 6, the node_bundler = "nft" setting prevents a common deployment error where native Node.js modules fail to bundle correctly.
Module 02

Building Your Main Website

This module covers designing and coding your entire public-facing website. We'll work in a single HTML file, define your visual identity in CSS, build every section a service business needs, and optimize the whole thing for mobile. The process is iterative - describe, generate, review, refine, repeat.

The single-file approach

For a small business website, everything can live in one index.html file. Your CSS goes in a <style> block in the <head>. Your JavaScript goes in a <script> block just before the closing </body> tag. This approach has real advantages: no broken imports, nothing to misconfigure, easier to hand off, and simpler to debug.

The tradeoff is that one file can get long. That's fine. Modern browsers handle it easily, and searching a single file for "pricing" or "FAQ" is faster than navigating folders of separate files.

How AI was used to build the site: The HTML, CSS, and JavaScript for every section was written by AI. The workflow: describe what you need in plain English → AI generates the code → review and test it in a browser → request changes → paste the final version into your file. For example: "Write a hero section with a full-width background, my headline 'Norfolk's Most Trusted Cleaners,' a short paragraph about the business, and two buttons: Book Now and View Pricing. Use the color variables I've defined." AI produces complete, working code. You paste it in, check the browser, and iterate.
Setting up your CSS design system

Before writing any layout code, define your brand's colors and fonts as CSS variables. This is one of the highest-leverage decisions you make early on - if you change your mind on a color later, you change one line instead of searching through hundreds of style rules.

/* Put this at the top of your <style> block */ :root { /* Brand colors */ --primary: #2C3E2D; /* Main dark color - headers, nav, footer */ --accent: #C1633A; /* Action color - buttons, links, highlights */ --light: #F5F0E8; /* Background and light text on dark sections */ --text: #1a1a1a; /* Body copy */ --text-soft: #555555; /* Secondary text, captions */ --border: #e0dbd3; /* Lines, card borders */ /* Typography */ --font-heading: 'Playfair Display', serif; --font-body: 'DM Sans', sans-serif; /* Spacing scale */ --space-sm: 12px; --space-md: 24px; --space-lg: 48px; --space-xl: 80px; }
Picking your fonts: Load them from Google Fonts for free. In the <head> of your HTML, add: <link href="https://fonts.googleapis.com/css2?family=Playfair+Display:wght@700&family=DM+Sans:wght@300;400;500&display=swap" rel="stylesheet">. Good pairings: Playfair Display + DM Sans (elegant), Fraunces + Inter (modern editorial), Cormorant Garamond + Jost (luxury). Pick two fonts maximum - one for headings, one for body text.
Essential sections for a service business

Every service business website needs the same core sections. Here's what each one must do and the most common mistakes people make building them:

Hero Section - Your headline, one sentence about what you do, and a primary call-to-action button. The hero has one job: make a new visitor immediately understand what you offer and what to do next. Avoid vague taglines like "Excellence in Every Service." Instead: "Residential Cleaning in Norfolk, VA - Book Online in Under 2 Minutes." Test it with someone who doesn't know your business. If they can't tell what you do in 5 seconds, rewrite it.
Services & Pricing - One card per service with the service name, a 1-2 sentence description, and a clear price (or price range). People leave websites that hide pricing. You don't need an exact quote system - just give them enough to know if they're in the right ballpark. If pricing varies too much, say "Starting at $X" and explain what affects the final price.
How It Works - 3 to 4 numbered steps describing your process from initial contact to delivered service. This reduces the anxiety first-time buyers feel about the unknown. Keep it concrete: "1. Fill out the booking form. 2. We confirm your appointment by email within 2 hours. 3. Our team arrives on the agreed date." Vague steps like "We provide quality service" are useless here.
About / Trust Section - Who you are, how long you've been operating, relevant credentials, insurance status, certifications, and any associations or accreditations. Photos of real people significantly outperform stock photography. People hire businesses they trust. This section exists to build that trust before you've ever met them.
Testimonials / Reviews - Real quotes from real clients with their name (and optionally their city or profession). If you have Google reviews, link directly to your Google Business profile so visitors can verify them. Three genuine testimonials beat ten that look fake.
FAQ - Answer the 6-8 questions you get asked most often. "Do you bring your own supplies?" "Are you insured?" "What happens if I need to reschedule?" This section does double duty: it reduces inbound inquiries and it's excellent for SEO because real questions people search for end up on your page.
Booking / Contact Form - The action you want visitors to take. Keep it to the minimum fields you actually need to follow up. Name, email, phone, service type, and preferred date covers almost every service business. Every additional field reduces conversion rate. Forms connect to your database in Module 3.
Footer - Business name, contact email, phone number, social media links, service area, and a short copyright line. Optionally: a link to your privacy policy (increasingly expected and legally required in some states for contact forms that collect personal data).
Promotional popup

A timed popup - appearing a few seconds after page load - announcing a discount, a seasonal offer, or a new service can meaningfully increase conversions. The key is making it dismissable and making sure it only appears once per visitor.

/* CSS: popup overlay, hidden by default */ #promo-popup { display: none; position: fixed; inset: 0; background: rgba(0,0,0,0.55); z-index: 9999; align-items: center; justify-content: center; } #promo-popup.visible { display: flex; }
// JavaScript: show after 4 seconds, but only once per visitor function initPromoPopup() { const alreadySeen = localStorage.getItem('promo_dismissed'); if (alreadySeen) return; // They've already seen it, skip setTimeout(() => { document.getElementById('promo-popup').classList.add('visible'); }, 4000); } function dismissPromo() { document.getElementById('promo-popup').classList.remove('visible'); localStorage.setItem('promo_dismissed', 'true'); } initPromoPopup();
Don't abuse popups. A popup that fires instantly, covers the whole screen, is hard to close on mobile, and appears on every visit will hurt your bounce rate. The formula that works: delay it (3-5 seconds), make the close button obvious and large, and use localStorage so it never fires again after being dismissed.
AI prompt that generated the popup code: "Add a full-screen popup overlay to my website that appears after 4 seconds. It should show a 10% off discount for first-time bookings with a code in bold, a brief description, and a large close button. It should never show again to visitors who have already dismissed it. Use the color variables I've defined at the top of my CSS."
Availability unavailable notice

There will be times when you go on vacation, take on a big contract, or just get fully booked. You need a way to tell website visitors you're not taking bookings without taking down the whole site or hand-editing every page.

// At the top of your <script> block - flip this when needed const BOOKING_UNAVAILABLE = false; // change to true to disable bookings const UNAVAILABLE_MESSAGE = "We're fully booked through March. Check back April 1st, or leave your email below to be notified when we reopen bookings."; // Apply it when the page loads document.addEventListener('DOMContentLoaded', () => { if (BOOKING_UNAVAILABLE) { document.getElementById('booking-form').style.display = 'none'; document.getElementById('unavailable-notice').style.display = 'block'; document.getElementById('unavailable-notice').textContent = UNAVAILABLE_MESSAGE; } });

Change one variable, save, push - done. The message is editable too, so you can tell people why you're unavailable and what to do instead (leave an email, check back on a date, call you directly).

Mobile optimization

More than half of all website visitors are on phones. Your site must work on a 390px screen. This is not optional. Google also uses the mobile version of your site as the primary version for search ranking (called mobile-first indexing).

Make sure this tag is in your <head>. Without it, mobile browsers render your desktop site at full width and scale it down, making everything tiny:
<meta name="viewport" content="width=device-width, initial-scale=1.0">
Add mobile overrides using CSS media queries at the bottom of your <style> block:
/* Mobile styles - applied on screens narrower than 640px */ @media (max-width: 640px) { .services-grid { grid-template-columns: 1fr; /* Stack cards vertically */ gap: 16px; } h1 { font-size: 32px; } /* Reduce headline size */ .hero { padding: 48px 20px; } /* Reduce padding */ .nav-links { display: none; } /* Hide desktop nav (add hamburger) */ }
Test continuously. In Chrome, press F12 to open DevTools, then click the phone/tablet icon at the top of the DevTools panel. You can switch between different device sizes. Select "iPhone SE" (375px wide) as your minimum bar - if it looks good there, it'll look good everywhere.
Before going live, test on a real phone. The DevTools preview is good but not perfect. Colors, tap target sizes, and font legibility can look different on an actual device screen. Email yourself the Netlify URL and check it on your phone.
Common Mobile Issues
Horizontal scrollbar appears on mobile
Something is wider than the screen. The usual culprits: a width: 100vw element that doesn't account for scrollbar width, an element with a fixed min-width wider than the viewport, or an overflowing flex container. Add overflow-x: hidden to the body as a temporary fix, then use the DevTools inspector to find the offending element.
Buttons are too small to tap
Apple's Human Interface Guidelines specify a minimum tap target of 44×44px. Add min-height: 44px; padding: 12px 20px; to all clickable buttons and links on mobile.
Text is readable on desktop but looks too small on phone
Base body font should be at minimum 16px on mobile. Below 16px, iOS Safari automatically zooms in when users tap input fields, which breaks your layout. Use your media query to set font-size: 16px on body for mobile.
AI was used for mobile fixes throughout: When a layout issue appeared on mobile (e.g., "the testimonials section has a gap on the right side on iPhone"), describing the problem to AI - including the relevant CSS and HTML - consistently produced the correct fix. AI is particularly fast at diagnosing overflow and flexbox issues.
Module 03

Setting Up a Backend Database

A static HTML file can only show information that was written into it at build time. A database lets your site show information that changes - your current availability, a specific client's invoice, a booking confirmation. This module covers Supabase: a free, powerful database that your website can read from and write to in real time.

Do you actually need a database?
Without a database
To update your availability, you edit the HTML file, commit, and push. Every change requires a new deployment. Clients see whatever was true when you last deployed - not what's true right now.
With a database
Your website reads live data every time a visitor loads it. You update your calendar, and the availability on your site updates automatically - no touching the HTML file at all.

If your website needs to show availability, process bookings, store client information, generate invoices, or display anything that changes more than once a month - you need a database. Everything from Module 4 onward depends on this.

Setting up Supabase

Supabase is an open-source Firebase alternative built on PostgreSQL. It gives you a database, a REST API to query it, a JavaScript client library, real-time subscriptions, authentication, and serverless functions - all on a free tier that is more than sufficient for a small business site.

Go to supabase.com, create a free account, and click "New Project." Give it a name (your business name works), set a strong database password (save this somewhere secure - you'll need it if you ever connect via direct SQL), and choose the region geographically closest to you for minimum latency.
Wait 2-3 minutes for your project to be provisioned. Once the green "healthy" indicator appears, go to Settings → API. You'll see two keys:
  • anon / public key - Safe to use in your HTML files. This key is controlled by Row Level Security (RLS) rules you set in Supabase. It can only read/write what you explicitly allow.
  • service_role / secret key - Has full admin access to your database. Never, ever put this in an HTML file or commit it to GitHub. Only use it in serverless functions as an environment variable.
Copy both keys to a secure note. You'll need the anon key in your frontend code and the service_role key when setting up Netlify Functions and Supabase Edge Functions.
Never commit your service_role key to GitHub. The anon key is safe because it's governed by Row Level Security. The service_role key bypasses all security rules. If it gets into a public GitHub repo, someone can delete your entire database, read all your client data, and run arbitrary SQL. Store it only as an environment variable in Netlify and Supabase secrets.
Creating your first database table

Tables in Supabase work like spreadsheets. Each row is a record. Each column is a field. You design the structure - Supabase handles the storage, indexing, and API.

In Supabase, go to Table Editor → New table. Name it descriptively in lowercase with underscores: availability, invoices, bookings, contact_submissions.
Every table automatically gets an id column (auto-incrementing integer or UUID). Add your columns based on what data you need. For each column, you'll choose a data type:
TypeUse forExamples
textAny text/stringclient name, email, notes
int4Whole numbersslot count, quantity, order number
numericDecimal numbersprice ($125.00), percentage
boolTrue/falseis_paid, is_confirmed, is_active
dateCalendar datesappointment_date, invoice_date
timestamptzDate + time + timezonecreated_at, updated_at, paid_at
Enable Row Level Security (RLS) on every table (it's a toggle when creating the table). Then create policies that define who can read or write. For availability data that anyone can read: create a policy for SELECT that allows anon role with condition true (anyone can read). For writes, restrict to service_role only.
Common Issues
API returns an empty array even though the table has data
Row Level Security (RLS) is blocking the read. Go to Supabase → Authentication → Policies and make sure you have a SELECT policy on the table that allows the anon role. Alternatively, in Table Editor you can temporarily disable RLS to confirm this is the issue, then re-enable and add the policy.
Supabase project is "paused" and not responding
Free Supabase projects automatically pause after 7 days of inactivity (no API requests). Log into supabase.com, find your project, and click "Restore." It takes 1-2 minutes. To prevent this, make sure your cron job (Module 5) runs at least once a week - even a no-op request counts as activity.
I accidentally deleted a table with data in it
Supabase does not provide point-in-time recovery on the free plan. Once a table is deleted, the data is gone. Paid plans include database backups. For a production site collecting real client data, the Pro plan ($25/month) is worth it for the backup protection alone.
AI designed the table schemas. Rather than guessing which columns were needed and what types to use, the table structure for availability, invoices, and bookings was described to AI in plain English: "I need a table to track daily availability. Each day can have up to 3 bookings in morning, afternoon, or evening slots. I need to know the date and how many slots are taken in each time window." AI returned a complete table design with column names, types, and the rationale for each decision.
Supabase Edge Functions

Edge Functions are small server-side scripts (written in TypeScript) that run on Supabase's servers. They're for tasks that must happen on the backend - using your secret keys, calling external APIs, running scheduled jobs. Think of them as serverless functions that have automatic access to your Supabase database.

Install the Supabase CLI. On Mac with Homebrew: brew install supabase/tap/supabase. On Windows: download from the GitHub releases page at github.com/supabase/cli/releases.
Log in: supabase login. This opens a browser window for authentication.
Link your local project to your Supabase project: supabase link --project-ref your-project-id. Find your project ID in Supabase → Settings → General.
Create a new function: supabase functions new function-name. This creates a supabase/functions/function-name/index.ts file.
Write your function logic in the TypeScript file. See Module 5 for the full calendar sync function.
Deploy: supabase functions deploy function-name --no-verify-jwt. The --no-verify-jwt flag is required if you're calling this function from a cron job or external service rather than from an authenticated user session.
Set any secrets the function needs: supabase secrets set CALENDAR_REFRESH_TOKEN=your-token-here. Secrets are environment variables available inside the function as Deno.env.get('CALENDAR_REFRESH_TOKEN').
Common Issues
"supabase: command not found" after installing on Mac
The Homebrew binary path isn't in your shell's PATH. Run echo 'export PATH="/opt/homebrew/bin:$PATH"' >> ~/.zshrc && source ~/.zshrc (for Zsh, which is the default on modern Macs) and try again.
Function deploys but returns a 500 error when called
Check the function logs: Supabase → Edge Functions → your function → Logs. The error details will tell you exactly what line failed and why. Common causes: a missing secret (typo in the secret name), a JSON parse error on an API response, or an incorrect Supabase database query.
"JWT verification failed" error
You're calling a function that requires a user JWT token, but you're calling it without one. Either redeploy with --no-verify-jwt if the function should be publicly callable (like from a cron job), or pass the correct authorization header if it should require authentication.
Module 04

Live Availability Display

This module builds the system that shows your real-time availability on your public website - a calendar grid where visitors can see which days and time slots are open, filling up, or fully booked. The display reads from your Supabase database and updates automatically when your calendar syncs.

How the system is designed

There are three connected parts:

The database table - stores a row for each date with slot counts (morning, afternoon, evening). A date with no row means all slots are fully open.
The sync function - reads your actual calendar (covered in Module 5), counts booked slots per day, and writes those counts to the database once per hour.
The frontend display - when a visitor loads your website, JavaScript fetches the next 30 days of data from Supabase and renders a color-coded availability calendar.

You set a maximum number of bookings per slot (e.g., 3). The frontend compares the count to the max and assigns a status: open, filling up, or unavailable.

Fetching availability from your website

Your frontend HTML calls Supabase's REST API directly using the browser's built-in fetch() function. No library required. The anon key is safe to include here because your Row Level Security policy only allows reads.

const SUPABASE_URL = 'https://yourprojectid.supabase.co'; const SUPABASE_ANON_KEY = 'your-anon-key-here'; const MAX_PER_SLOT = 3; // adjust to your capacity async function loadAvailability() { const today = new Date().toISOString().slice(0, 10); // "2024-03-15" const response = await fetch( `${SUPABASE_URL}/rest/v1/availability?date=gte.${today}&order=date.asc&limit=30`, { headers: { 'apikey': SUPABASE_ANON_KEY, 'Authorization': `Bearer ${SUPABASE_ANON_KEY}` } } ); if (!response.ok) { console.error('Failed to load availability:', response.status); return; } const data = await response.json(); renderAvailabilityCalendar(data); }
Why include both apikey and Authorization headers? Supabase requires both. The apikey header identifies your project. The Authorization: Bearer header is the authentication token. For public/anon requests they're the same value - the anon key.
Rendering the availability grid

Calendar Sync Automation

This is the most technically complex part of the build - connecting your actual calendar to your website so that when you add a booking to your calendar, your website's availability display updates automatically within the hour. No manual updates, no double entry. This module covers OAuth2 authentication, the sync script itself, and setting up an automated hourly cron job.

The complete sync flow

Here's what happens end to end, every hour:

A cron job fires a request to your Supabase Edge Function (the sync script).
The function uses your stored refresh token to get a fresh access token from your calendar provider (Zoho, Google, etc.).
It fetches all calendar events for the next 30 days.
It reads each event's title to determine which slot it occupies (morning / afternoon / evening).
It counts how many events fall in each slot for each date.
It upserts (insert or update) those counts into your Supabase availability table.
Your website reads the updated data the next time a visitor loads the availability section.
Naming your calendar events: The sync script identifies which time slot a booking belongs to by reading the event title. You need to include the slot name in the title consistently: "Window Cleaning - Morning," "Deep Clean - Afternoon," "Move-Out Clean - Evening." You choose the keywords - just use them consistently on every event you want tracked.
OAuth2 - Getting calendar access

OAuth2 is the authentication standard that lets your application access your calendar on your behalf, without storing your password. You do a one-time setup to generate a refresh token. Your sync script uses that refresh token to silently get a fresh access token (which expires hourly) whenever it needs to read your calendar.

For Zoho Calendar: Log into Zoho Developer Console at api-console.zoho.com. Click "Add Client" and select "Self Client" (this is for scripts that access your own data, not other users' data). Note your Client ID and Client Secret.
For Google Calendar: Go to Google Cloud Console at console.cloud.google.com. Create a project, enable the Google Calendar API, and create OAuth2 credentials. Download the credentials JSON file.
Generate an authorization code. For Zoho, in the Self Client console, request a code with scope ZohoCalendar.event.READ. This code expires in 1-3 minutes. For Google, run a local OAuth flow to get the refresh token (AI can generate this script for you).
Exchange the short-lived code for a refresh token. Run this script immediately after getting the code:
# Python script - run this once to get your refresh token import requests CLIENT_ID = "your_client_id" CLIENT_SECRET = "your_client_secret" AUTH_CODE = "the_code_you_just_got" # Expires in ~1 minute! response = requests.post("https://accounts.zoho.com/oauth/v2/token", data={ "grant_type": "authorization_code", "client_id": CLIENT_ID, "client_secret": CLIENT_SECRET, "redirect_uri": "https://localhost", # Must match what you set in console "code": AUTH_CODE }) print(response.json()) # Copy the "refresh_token" value
Copy the refresh_token from the response. Store it as a Supabase secret: supabase secrets set ZOHO_REFRESH_TOKEN=your-token-value. Also store the client credentials: supabase secrets set ZOHO_CLIENT_ID=xxx and supabase secrets set ZOHO_CLIENT_SECRET=xxx.
Common Issues - OAuth2 is the #1 Source of Problems
"invalid_code" or "code expired" error when exchanging for refresh token
The authorization code expired before you could use it. They're valid for 60-180 seconds. Have your token exchange script ready to run before you generate the code. Copy the code, immediately switch windows, paste it, and run the script. Don't take any breaks in between.
"redirect_uri_mismatch" error
The redirect_uri in your token exchange request must exactly match what you registered in the developer console - including the protocol (https vs http), trailing slash, and any path. https://localhost and http://localhost are different. Check for exact character-by-character match.
Refresh token stops working after a few months
Zoho refresh tokens are typically long-lived but can expire after extended periods of inactivity (often 6 months to 1 year) or if you revoke app permissions. Google refresh tokens can expire if the OAuth consent screen is in "testing" mode with unverified status. If your availability sync suddenly stops, this is the first thing to check. Re-run the token generation process and update the Supabase secret.
"insufficient_scope" error when fetching calendar events
The scope you requested when generating the authorization code doesn't include the permission to read events. For Zoho, make sure you requested ZohoCalendar.event.READ. For Google, make sure you included https://www.googleapis.com/auth/calendar.readonly. You'll need to generate a new authorization code and refresh token with the correct scope.

Automated Email Notifications

Every time a client pays an invoice, you receive an automatic email with the details - client name, amount, invoice ID, and timestamp. This module covers setting up Resend (a free transactional email API), verifying your sending domain, and wiring the notification into your payment confirmation function.

Why Resend, and what the alternatives are

Resend is a developer-focused email API with a free tier of 3,000 emails per month and 100 per day. It supports sending from your own domain, which means emails come from hello@yourbusiness.com rather than a generic service address - significantly better for deliverability and professionalism.

Alternatives worth knowing about: SendGrid (larger scale, slightly more complex setup), Postmark (excellent deliverability, focused on transactional email), Mailgun (popular with developers). For this use case - a small volume of payment notification emails - Resend is the simplest choice.

Verifying your sending domain

To send email from your own domain address, you must prove to email servers worldwide that you're authorized to send from it. This is done via DNS records. Without this, your emails will go to spam or be rejected outright.

Create a Resend account at resend.com. Go to Domains → Add Domain and enter your domain name (e.g., yourbusiness.com).
Resend provides 3 DNS records to add. These are:
  • SPF - A TXT record that lists Resend as an authorized sender for your domain
  • DKIM - A TXT record with a cryptographic key that signs your outgoing emails, proving they're legitimate
  • DMARC - A TXT record that tells receiving servers what to do with emails that fail SPF or DKIM (reject, quarantine, or just report)
Log into your domain registrar (where you bought your domain - GoDaddy, Namecheap, Squarespace, Google Domains, etc.) and navigate to DNS settings. Add each record exactly as provided by Resend. The record type, name, and value must be exact.
Click "Verify" in Resend. DNS changes propagate globally over time - typically 15 minutes to a few hours, but can occasionally take up to 24-48 hours in edge cases.
Create an API key: Resend → API Keys → Create API Key. Copy it and add it to Netlify environment variables as RESEND_API_KEY. Also add your email address as OWNER_EMAIL.
Common Issues
Resend says "DNS records not verified" after 24 hours
One or more records wasn't entered correctly. Common mistake: the DKIM record name should be something like resend._domainkey - some registrars automatically append your domain to the name, resulting in resend._domainkey.yourdomain.com.yourdomain.com. If your registrar auto-appends the domain, enter just resend._domainkey without your domain. Check each record using a tool like mxtoolbox.com.
Emails send successfully but end up in spam
Most commonly caused by DMARC not being set up, or the DMARC policy being set to none (just monitoring). Make sure all three records (SPF, DKIM, DMARC) are verified in Resend. Also check that your email subject lines don't look like spam (avoid ALL CAPS, excessive punctuation, or words like FREE, URGENT, ACT NOW).

Linking auth users to Firestore client documents

When a client creates an account, Firebase Authentication assigns them a unique UID (e.g., uid: "wX9k2mA..."). Your Firestore client documents need to store this UID so the security rules can match the logged-in user to their data.

The approach: when you create a client in the admin dashboard, you also create their Firebase Auth account programmatically. Firebase returns the new UID, which you then save into the client's Firestore document. From that point on, the UID is the link between auth and data.

// In your admin dashboard - creating a new client with auth account async function createClientWithAuth(name, email, tempPassword) { // 1. Create the Firebase Auth account const userRecord = await firebase.auth() .createUserWithEmailAndPassword(email, tempPassword); const uid = userRecord.user.uid; // 2. Generate their client code const clientCode = await generateUniqueClientCode(); // 3. Create the Firestore document with the UID stored await db.collection('clients').doc(clientCode).set({ name, email, uid, // critical - links this doc to the auth account clientCode, createdAt: firebase.firestore.FieldValue.serverTimestamp(), registered: true }); // 4. Send them a password reset so they set their own password await firebase.auth().sendPasswordResetEmail(email); return { uid, clientCode }; }
Temporary passwords: Generate a random temporary password (e.g., crypto.randomUUID()) when creating the account. Immediately send a password reset email. The client sets their own password before they ever log in. You never store or see their actual password.

AI also flagged that createUserWithEmailAndPassword signs the admin in as the new user, which is a side effect that needs to be handled. The fix: use the Firebase Admin SDK in a Netlify Function instead of the client SDK, so the admin session is not affected.
Firestore security rules

This is the most important part of the entire client portal. Security rules determine what data each authenticated user can read. Without correct rules, any logged-in client could read any other client's data just by guessing a document path.

The rules below allow a client to read their own document (matched by UID) and their own subcollections. They cannot read any other client's document, regardless of whether they know the ID.

// Firebase Console → Firestore → Rules rules_version = '2'; service cloud.firestore { match /databases/{database}/documents { // Clients collection match /clients/{clientCode} { // A client can only read their OWN document // request.auth.uid must match the uid field stored in the document allow read: if request.auth != null && request.auth.uid == resource.data.uid; // Only admin (service role via Functions) can write allow write: if false; // Sessions subcollection - same rule match /sessions/{sessionId} { allow read: if request.auth != null && request.auth.uid == get( /databases/$(database)/documents/clients/$(clientCode) ).data.uid; allow write: if false; } // Documents subcollection match /documents/{docId} { allow read: if request.auth != null && request.auth.uid == get( /databases/$(database)/documents/clients/$(clientCode) ).data.uid; allow write: if false; } } } }
Common Issues - Security Rules
Rules simulator shows "allow" but live app gets permission denied
The simulator uses the document data at simulation time. If the uid field was not set correctly when the document was created (e.g., it was added in a separate update rather than in the initial set() call), the field may be missing from older documents. Check the actual Firestore document in the console and confirm the uid field is present and matches the auth UID exactly.
Subcollection reads fail even though the parent document read works
Subcollection rules require a get() call to fetch the parent document's UID for comparison. This is a cross-document read and counts against your Firestore read quota. More importantly, it will fail if the client does not have read permission on the parent document itself. Make sure the parent read rule is passing first before debugging subcollection rules.
"Missing or insufficient permissions" on first login
Firebase Auth tokens take a moment to propagate. If your code fetches Firestore data immediately after signInWithEmailAndPassword resolves, the auth token may not yet be attached to the request. Wrap your data fetch in an onAuthStateChanged listener instead of calling it directly after sign-in. The listener fires once the token is confirmed valid.

Common Issues - Dashboard
Invoices tab shows nothing even though invoices exist in Supabase
The email used in the Supabase invoice record must exactly match the email in Firebase Auth (including case). Check both. Also verify the Supabase RLS policy allows the read - temporarily disable RLS to confirm data is there, then re-enable and debug the policy.
Document download URLs expire and stop working
Firebase Storage download URLs from getDownloadURL() do not expire if the Storage security rules allow the read - they are access-token URLs tied to the authenticated user. If links are expiring, it is usually because the client signed out and the URL requires authentication. The solution: generate URLs server-side using the Admin SDK (via a Netlify Function), which produces URLs that do not require client auth. Or accept that clients must be signed in to download, which is the correct behavior anyway.
All tabs load slowly on first open
Promise.all in loadClientData fires all three requests in parallel, which is already the fastest approach. If it still feels slow, add skeleton loading placeholders (grey boxes that show while data loads) so the page feels instant even if the data takes a moment. This is a perceived performance fix rather than a real one, but it significantly improves how the portal feels to use.
Module 04

Admin Integration

The client portal does not exist in isolation. When you add a client in the admin dashboard, their portal account should be created automatically. When you upload a document from the admin side, it should appear in the client's portal immediately. This module covers wiring the admin dashboard to the portal so both sides stay in sync without manual steps.

Creating portal accounts from the admin dashboard

Adding "create portal account" to your existing admin new-client flow requires one additional step: calling a Netlify Function that uses the Firebase Admin SDK to create the auth account server-side. This avoids the issue of createUserWithEmailAndPassword signing the admin out of their own session.

// netlify/functions/create-client-auth.js // Uses Firebase Admin SDK - requires FIREBASE_SERVICE_ACCOUNT env variable const admin = require('firebase-admin'); if (!admin.apps.length) { admin.initializeApp({ credential: admin.credential.cert( JSON.parse(process.env.FIREBASE_SERVICE_ACCOUNT) ) }); } exports.handler = async (event) => { const { email, clientCode } = JSON.parse(event.body); try { // Create the auth account const user = await admin.auth().createUser({ email }); // Store the UID in the Firestore client document await admin.firestore() .collection('clients').doc(clientCode) .update({ uid: user.uid }); // Generate a password reset link (client sets their own password) const link = await admin.auth() .generatePasswordResetLink(email); // Send the welcome email via Resend await sendWelcomeEmail(email, link); // see below return { statusCode: 200, body: JSON.stringify({ uid: user.uid }) }; } catch (err) { return { statusCode: 500, body: JSON.stringify({ error: err.message }) }; } };
Firebase Admin SDK setup: The Admin SDK requires a service account key JSON file from Firebase. Go to Firebase Console → Project settings → Service accounts → Generate new private key. Download the JSON. In Netlify, add it as an environment variable: FIREBASE_SERVICE_ACCOUNT with the entire JSON as the value (minified, no line breaks). Add firebase-admin to your package.json dependencies and run npm install before deploying.
The welcome email

When a client's portal account is created, send them a welcome email with their login link and instructions. The password reset link Firebase generates is how they set their first password - frame it as "set up your account" rather than "reset your password."

async function sendWelcomeEmail(email, passwordSetupLink) { await fetch('https://api.resend.com/emails', { method: 'POST', headers: { 'Authorization': `Bearer ${process.env.RESEND_API_KEY}`, 'Content-Type': 'application/json' }, body: JSON.stringify({ from: process.env.FROM_EMAIL, to: email, subject: 'Your client portal is ready', html: ` <div style="font-family: Georgia, serif; max-width: 540px; margin: 0 auto;"> <h2>Your account is set up.</h2> <p>You now have access to your client portal, where you can view your invoices, session history, and shared documents.</p> <p style="margin: 28px 0;"> <a href="${passwordSetupLink}" style="background: #1e3a5f; color: white; padding: 13px 24px; text-decoration: none; border-radius: 5px; font-family: sans-serif;"> Set Up Your Password </a> </p> <p style="font-size: 13px; color: #6b7280;"> After setting your password, you can log in any time at <a href="${process.env.GUIDE_URL}/client-portal.html"> your portal </a>. This setup link expires in 24 hours. </p> </div> ` }) }); }
Uploading documents from the admin side

When you want to share a document with a client - a contract, a photo, a receipt - you upload it from the admin dashboard. The file goes to Firebase Storage and the metadata is written to the client's Firestore documents subcollection. It appears in their portal immediately.

async function uploadClientDocument(clientCode, file) { const storagePath = `clients/${clientCode}/${Date.now()}_${file.name}`; const storageRef = firebase.storage().ref(storagePath); // Upload the file const snapshot = await storageRef.put(file); // Save metadata to Firestore await db.collection('clients').doc(clientCode) .collection('documents') .add({ name: file.name, storagePath: storagePath, size: file.size, type: file.type, uploadedAt: firebase.firestore.FieldValue.serverTimestamp() }); }
File size limits: Firebase Storage on the free (Spark) plan allows up to 5GB total storage. There is no per-file limit enforced by Firebase, but set one in your upload UI: if (file.size > 10 * 1024 * 1024) { alert('File must be under 10MB'); return; }. Large files cause slow uploads with no progress feedback, which looks like the form is broken.
Disabling a client's portal access

If a client relationship ends, you can disable their portal access without deleting their data. Firebase Authentication lets you disable an account - they cannot sign in, but their Firestore documents and Storage files remain intact.

// In your admin dashboard - disable portal access async function disableClientPortal(clientCode) { const clientDoc = await db.collection('clients').doc(clientCode).get(); const uid = clientDoc.data().uid; if (!uid) { alert('This client does not have a portal account.'); return; } // Call a Netlify Function that uses Admin SDK to disable the account await fetch('/.netlify/functions/disable-client-auth', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ uid }) }); // Mark as disabled in Firestore await db.collection('clients').doc(clientCode) .update({ portalDisabled: true }); alert('Portal access disabled. The client cannot sign in.'); }
Common Issues - Admin Integration
"Cannot find module firebase-admin" when deploying the Netlify Function
The firebase-admin package must be listed in a package.json at the root of your project. Create one if it does not exist: npm init -y, then npm install firebase-admin. Netlify reads package.json and installs dependencies automatically during the build. Make sure your netlify.toml has node_bundler = "nft".
FIREBASE_SERVICE_ACCOUNT environment variable causes a JSON parse error
When pasting the service account JSON into Netlify's environment variable field, it must be on a single line with no line breaks. Use a minifier or run cat serviceAccount.json | python3 -m json.tool --compact to collapse it. Line breaks inside the JSON value will cause a parse failure when the function reads it with JSON.parse(process.env.FIREBASE_SERVICE_ACCOUNT).
Welcome email password setup link expires before the client uses it
Firebase password reset links expire after one hour by default. You can set a custom expiry duration using the Admin SDK: pass an ActionCodeSettings object to generatePasswordResetLink() with a longer expiresIn. Alternatively, note in the welcome email that the link is time-limited and include a clear instruction for what to do if it expires (go to the login page and click "Forgot password").
