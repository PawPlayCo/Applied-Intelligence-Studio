Module 01

Firebase Authentication Setup

Before building any portal screens, you need Firebase Authentication configured correctly. This module covers enabling email/password auth, writing the Firestore security rules that keep each client's data private, and understanding how Firebase links an authenticated user to their documents in the database.

Why Firebase Authentication

Firebase Authentication handles the hardest parts of user accounts for you: secure password hashing, session tokens, password reset emails, and account management. You do not store passwords - Firebase does, and it does it correctly. Your job is to connect auth state to your data.

The client portal uses two Firebase products together: Authentication (who is this person?) and Firestore (what data are they allowed to see?). Security rules sit between them - they check the authenticated user's UID against the data being requested and allow or deny the read.

Prerequisite: This add-on builds on the staff portal and admin dashboard (Add-on 03). Your Firebase project, Firestore database, and client collection should already exist. If they do not, complete Add-on 03 first.
Enabling email/password authentication
In Firebase Console, go to your project and click Authentication in the left sidebar. Click "Get started" if you have not used it before.
Click Sign-in method. Find Email/Password and click the pencil icon. Toggle Enable on. Leave "Email link (passwordless sign-in)" off. Click Save.
Go to Authentication → Settings → Authorized domains. Your Netlify domain should already be there from previous setup. If not, add it now: yourdomain.com and yourdomain.netlify.app.
In Authentication → Templates, customize the password reset email. Set the sender name to your business name, and update the subject line and body to match your brand voice. Firebase sends this automatically when clients click "Forgot password."
Custom email domain for auth emails: By default, Firebase sends password reset emails from noreply@[your-project].firebaseapp.com. To send from your own domain, go to Authentication → Templates → Edit → Customize action URL. This requires a verified sending domain - the same one you set up in Resend (Add-on 02) works for this.
Linking auth users to Firestore client documents

When a client creates an account, Firebase Authentication assigns them a unique UID (e.g., uid: "wX9k2mA..."). Your Firestore client documents need to store this UID so the security rules can match the logged-in user to their data.

The approach: when you create a client in the admin dashboard, you also create their Firebase Auth account programmatically. Firebase returns the new UID, which you then save into the client's Firestore document. From that point on, the UID is the link between auth and data.

// In your admin dashboard - creating a new client with auth account async function createClientWithAuth(name, email, tempPassword) { // 1. Create the Firebase Auth account const userRecord = await firebase.auth() .createUserWithEmailAndPassword(email, tempPassword); const uid = userRecord.user.uid; // 2. Generate their client code const clientCode = await generateUniqueClientCode(); // 3. Create the Firestore document with the UID stored await db.collection('clients').doc(clientCode).set({ name, email, uid, // critical - links this doc to the auth account clientCode, createdAt: firebase.firestore.FieldValue.serverTimestamp(), registered: true }); // 4. Send them a password reset so they set their own password await firebase.auth().sendPasswordResetEmail(email); return { uid, clientCode }; }
Temporary passwords: Generate a random temporary password (e.g., crypto.randomUUID()) when creating the account. Immediately send a password reset email. The client sets their own password before they ever log in. You never store or see their actual password.
AI used here: The client creation flow - including the correct order of operations (create auth first, get UID, then create Firestore doc) and the password reset email trigger - was written by AI. Getting the sequence wrong causes orphaned auth accounts with no matching Firestore data, which is difficult to debug. AI also flagged that createUserWithEmailAndPassword signs the admin in as the new user, which is a side effect that needs to be handled. The fix: use the Firebase Admin SDK in a Netlify Function instead of the client SDK, so the admin session is not affected.
Firestore security rules

This is the most important part of the entire client portal. Security rules determine what data each authenticated user can read. Without correct rules, any logged-in client could read any other client's data just by guessing a document path.

The rules below allow a client to read their own document (matched by UID) and their own subcollections. They cannot read any other client's document, regardless of whether they know the ID.

// Firebase Console → Firestore → Rules rules_version = '2'; service cloud.firestore { match /databases/{database}/documents { // Clients collection match /clients/{clientCode} { // A client can only read their OWN document // request.auth.uid must match the uid field stored in the document allow read: if request.auth != null && request.auth.uid == resource.data.uid; // Only admin (service role via Functions) can write allow write: if false; // Sessions subcollection - same rule match /sessions/{sessionId} { allow read: if request.auth != null && request.auth.uid == get( /databases/$(database)/documents/clients/$(clientCode) ).data.uid; allow write: if false; } // Documents subcollection match /documents/{docId} { allow read: if request.auth != null && request.auth.uid == get( /databases/$(database)/documents/clients/$(clientCode) ).data.uid; allow write: if false; } } } }
Common Issues - Security Rules
Rules simulator shows "allow" but live app gets permission denied
The simulator uses the document data at simulation time. If the uid field was not set correctly when the document was created (e.g., it was added in a separate update rather than in the initial set() call), the field may be missing from older documents. Check the actual Firestore document in the console and confirm the uid field is present and matches the auth UID exactly.
Subcollection reads fail even though the parent document read works
Subcollection rules require a get() call to fetch the parent document's UID for comparison. This is a cross-document read and counts against your Firestore read quota. More importantly, it will fail if the client does not have read permission on the parent document itself. Make sure the parent read rule is passing first before debugging subcollection rules.
"Missing or insufficient permissions" on first login
Firebase Auth tokens take a moment to propagate. If your code fetches Firestore data immediately after signInWithEmailAndPassword resolves, the auth token may not yet be attached to the request. Wrap your data fetch in an onAuthStateChanged listener instead of calling it directly after sign-in. The listener fires once the token is confirmed valid.
Module 02

Login and Registration Pages

The auth screens are the first thing clients see. This module covers the sign-in page, password reset flow, and handling the edge cases that will actually come up: wrong password, unverified email, session persistence across browser closes, and what to show while auth state is loading.

Page structure

The client portal lives as a separate HTML file in your project - client-portal.html. It handles two states: unauthenticated (shows the login form) and authenticated (shows the dashboard). No separate login page needed - a single file manages both views with JavaScript, the same panel-switching pattern from the admin dashboard.

/* Two top-level views inside client-portal.html */ #auth-view { display: block; } /* login/signup form */ #portal-view { display: none; } /* the actual dashboard */ /* Swap them based on auth state */ firebase.auth().onAuthStateChanged(user => { if (user) { document.getElementById('auth-view').style.display = 'none'; document.getElementById('portal-view').style.display = 'block'; loadClientData(user.uid); } else { document.getElementById('auth-view').style.display = 'block'; document.getElementById('portal-view').style.display = 'none'; } });
Session persistence: Firebase Authentication persists the session in localStorage by default. A client who signs in will still be signed in when they close and reopen their browser, until they explicitly sign out. You can change this to session-only (tab closes = signed out) with firebase.auth().setPersistence(firebase.auth.Auth.Persistence.SESSION) before calling sign-in.
The sign-in form
async function signIn() { const email = document.getElementById('email-input').value.trim(); const password = document.getElementById('password-input').value; const errorEl = document.getElementById('auth-error'); errorEl.textContent = ''; try { await firebase.auth().signInWithEmailAndPassword(email, password); // onAuthStateChanged handles the rest } catch (err) { // Map Firebase error codes to human-readable messages const messages = { 'auth/user-not-found': 'No account found with that email.', 'auth/wrong-password': 'Incorrect password. Try again or reset it below.', 'auth/invalid-email': 'Please enter a valid email address.', 'auth/too-many-requests': 'Too many attempts. Try again in a few minutes.', 'auth/user-disabled': 'This account has been disabled. Please contact us.', }; errorEl.textContent = messages[err.code] || 'Something went wrong. Please try again.'; } }
Never show Firebase's raw error messages to users. Messages like auth/user-not-found or Firebase: Error (auth/wrong-password) are jarring and expose implementation details. Always map them to plain English. The code above covers every error a legitimate user will encounter. Log the raw error to the console for your own debugging, but show only the friendly version.
Password reset flow
async function sendPasswordReset() { const email = document.getElementById('email-input').value.trim(); const msgEl = document.getElementById('reset-message'); if (!email) { msgEl.textContent = 'Enter your email address above first.'; return; } try { await firebase.auth().sendPasswordResetEmail(email); // Always show success - do not reveal whether the email exists msgEl.textContent = 'If that email has an account, a reset link is on its way. Check your spam folder too.'; } catch { msgEl.textContent = 'Could not send the reset email. Try again in a moment.'; } }
Do not reveal whether an email exists. If someone enters an email that has no account, show the same success message as if the reset email was sent. This prevents someone from using your password reset form to enumerate which emails have accounts. The code above does this correctly by catching all errors and showing a neutral message.
Loading state while auth resolves

onAuthStateChanged fires asynchronously - there is a brief moment on page load where Firebase does not yet know if the user is signed in. During this time, showing either the login form or the dashboard would cause a flash of the wrong view. The fix is a loading screen that covers both until auth state is known.

/* Show a loading overlay on page load */ #loading-overlay { position: fixed; inset: 0; background: #f7f7f5; display: flex; align-items: center; justify-content: center; z-index: 9999; } // Hide it once auth state is determined firebase.auth().onAuthStateChanged(user => { document.getElementById('loading-overlay').style.display = 'none'; // ... rest of auth handling });
Common Issues - Auth Pages
Client signs in successfully but the dashboard never appears
onAuthStateChanged fired but loadClientData likely threw an error before updating the UI. Open the browser console - if there is a Firestore permission error, the UID stored in Firestore does not match the authenticated user's UID. This usually means the client document was created before the auth account, or the UID was stored incorrectly. Check the client's Firestore document directly and compare the uid field to the UID in Firebase Authentication → Users.
Password reset email is going to spam
Firebase's default sending domain (firebaseapp.com) has reasonable deliverability but is not your domain. Until you configure a custom email domain in Firebase Authentication settings, some providers will flag it. For a production portal, set up the custom domain. Firebase's documentation covers this under Authentication → Templates → Customize action URL.
"The email address is already in use" when creating a client account
That email already has a Firebase Auth account in your project. Check Authentication → Users for the existing account. Either delete it (if it was a test) or link the existing UID to their Firestore document rather than creating a new auth account. Never create duplicate auth accounts for the same email.
Module 03

The Client Dashboard

The dashboard is what clients see after signing in - a tabbed layout showing their invoices, booking history, session notes, and uploaded documents. Each tab pulls from a different data source. This module covers loading the data, rendering each view, and making the whole thing feel fast and professional.

Dashboard layout

The same panel-switching pattern from the admin dashboard applies here - one HTML file, multiple content panels, only one visible at a time. The client sees a top navigation bar with their name and a sign-out button, and four tabs below: Invoices, Bookings, Session Notes, and Documents.

async function loadClientData(uid) { // Find the client's Firestore document by UID const snapshot = await db.collection('clients') .where('uid', '==', uid) .limit(1) .get(); if (snapshot.empty) { showError('Account not found. Please contact us.'); return; } const clientDoc = snapshot.docs[0]; const clientData = clientDoc.data(); const clientCode = clientDoc.id; // Display their name in the header document.getElementById('client-name').textContent = clientData.name?.split(' ')[0] || 'Welcome back'; // Load all tabs in parallel await Promise.all([ loadInvoices(clientData.email), loadSessions(clientCode), loadDocuments(clientCode), ]); showTab('invoices'); // default tab }
Why query by UID rather than storing the client code in auth? Firebase Authentication custom claims could store the client code, but that requires the Admin SDK and a server-side function to set them. Querying Firestore by UID is simpler and works entirely on the client side, at the cost of one extra read on login. For the scale of a small business portal, that is the right tradeoff.
Invoices tab - reading from Supabase

Invoice data lives in Supabase (set up in Add-on 02), not Firebase. The client portal reads it directly using the client's email as a lookup key, with the anon key. Make sure your Supabase Row Level Security policy allows reads where the email column matches the requesting user's email - or scope it through a Netlify Function if you want stricter control.

async function loadInvoices(email) { const res = await fetch( `${SUPABASE_URL}/rest/v1/invoices?email=eq.${encodeURIComponent(email)}&order=created_at.desc`, { headers: { 'apikey': SUPABASE_ANON_KEY } } ); const invoices = await res.json(); const container = document.getElementById('invoices-list'); if (!invoices.length) { container.innerHTML = '<p class="empty">No invoices yet.</p>'; return; } container.innerHTML = invoices.map(inv => ` <div class="invoice-row ${inv.paid ? 'paid' : 'unpaid'}"> <div class="inv-id">${inv.id}</div> <div class="inv-desc">${inv.description || inv.service}</div> <div class="inv-amount">$${parseFloat(inv.amount).toFixed(2)}</div> <div class="inv-status"> ${inv.paid ? '<span class="badge paid">Paid</span>' : `<a href="/invoice.html?id=${inv.id}" class="pay-btn">Pay Now</a>`} </div> </div> `).join(''); }
RLS policy for client invoice reads: In Supabase, create a SELECT policy on your invoices table: CREATE POLICY "clients_read_own_invoices" ON invoices FOR SELECT USING (email = current_setting('request.jwt.claims', true)::json->>'email'); - this requires JWT auth from Supabase. If you are using the anon key without user JWTs, a simpler approach is to route invoice reads through a Netlify Function that validates the Firebase auth token first, then returns only that client's invoices using the service role key.
Session history and notes tab
async function loadSessions(clientCode) { const snapshot = await db .collection('clients').doc(clientCode) .collection('sessions') .orderBy('date', 'desc') .get(); const container = document.getElementById('sessions-list'); if (snapshot.empty) { container.innerHTML = '<p class="empty">No sessions recorded yet.</p>'; return; } container.innerHTML = snapshot.docs.map(doc => { const s = doc.data(); return ` <div class="session-row"> <div class="session-date">${s.date}</div> <div class="session-service">${s.service || ''}</div> <div class="session-notes">${s.notes || 'No notes for this session.'}</div> ${s.completedBy ? \`<div class="session-by">${s.completedBy}</div>\` : ''} </div> `; }).join(''); }
What to show vs. what to hide: Staff notes in sessions may contain internal observations that were not meant for clients. Before going live, decide which session fields are client-facing. Either add a clientVisible: true/false field to each session document and filter on it, or create a separate client_notes field alongside your internal notes field. Do not show everything staff can see.
Documents tab - Firebase Storage

Firebase Storage holds files (contracts, photos, before/after images, receipts) scoped per client. Storage security rules mirror the Firestore rules - each client can only read files in their own folder.

In Firebase Console, go to Storage → Get started. Choose a location and start in production mode. You will set the rules manually.
Set Storage security rules:
rules_version = '2'; service firebase.storage { match /b/{bucket}/o { // Each client can only read their own folder match /clients/{clientCode}/{allPaths=**} { allow read: if request.auth != null && request.auth.uid == firestore.get( /databases/(default)/documents/clients/$(clientCode) ).data.uid; // Only admin uploads (via Functions) - clients cannot upload allow write: if false; } } }
Store document metadata in Firestore (name, upload date, type) and the Storage path. The client's portal reads the metadata from Firestore, then generates a download URL from Storage when the client clicks a file.
async function loadDocuments(clientCode) { const snapshot = await db .collection('clients').doc(clientCode) .collection('documents') .orderBy('uploadedAt', 'desc') .get(); const container = document.getElementById('documents-list'); if (snapshot.empty) { container.innerHTML = '<p class="empty">No documents shared yet.</p>'; return; } // Generate signed download URLs for each file const rows = await Promise.all(snapshot.docs.map(async doc => { const d = doc.data(); const storageRef = firebase.storage().ref(d.storagePath); const url = await storageRef.getDownloadURL(); return ` <div class="doc-row"> <div class="doc-name">${d.name}</div> <div class="doc-date">${d.uploadedAt?.toDate().toLocaleDateString()}</div> <a href="${url}" target="_blank" class="doc-download">Download</a> </div> `; })); container.innerHTML = rows.join(''); }
Common Issues - Dashboard
Invoices tab shows nothing even though invoices exist in Supabase
The email used in the Supabase invoice record must exactly match the email in Firebase Auth (including case). Check both. Also verify the Supabase RLS policy allows the read - temporarily disable RLS to confirm data is there, then re-enable and debug the policy.
Document download URLs expire and stop working
Firebase Storage download URLs from getDownloadURL() do not expire if the Storage security rules allow the read - they are access-token URLs tied to the authenticated user. If links are expiring, it is usually because the client signed out and the URL requires authentication. The solution: generate URLs server-side using the Admin SDK (via a Netlify Function), which produces URLs that do not require client auth. Or accept that clients must be signed in to download, which is the correct behavior anyway.
All tabs load slowly on first open
Promise.all in loadClientData fires all three requests in parallel, which is already the fastest approach. If it still feels slow, add skeleton loading placeholders (grey boxes that show while data loads) so the page feels instant even if the data takes a moment. This is a perceived performance fix rather than a real one, but it significantly improves how the portal feels to use.
Module 04

Admin Integration

The client portal does not exist in isolation. When you add a client in the admin dashboard, their portal account should be created automatically. When you upload a document from the admin side, it should appear in the client's portal immediately. This module covers wiring the admin dashboard to the portal so both sides stay in sync without manual steps.

Creating portal accounts from the admin dashboard

Adding "create portal account" to your existing admin new-client flow requires one additional step: calling a Netlify Function that uses the Firebase Admin SDK to create the auth account server-side. This avoids the issue of createUserWithEmailAndPassword signing the admin out of their own session.

// netlify/functions/create-client-auth.js // Uses Firebase Admin SDK - requires FIREBASE_SERVICE_ACCOUNT env variable const admin = require('firebase-admin'); if (!admin.apps.length) { admin.initializeApp({ credential: admin.credential.cert( JSON.parse(process.env.FIREBASE_SERVICE_ACCOUNT) ) }); } exports.handler = async (event) => { const { email, clientCode } = JSON.parse(event.body); try { // Create the auth account const user = await admin.auth().createUser({ email }); // Store the UID in the Firestore client document await admin.firestore() .collection('clients').doc(clientCode) .update({ uid: user.uid }); // Generate a password reset link (client sets their own password) const link = await admin.auth() .generatePasswordResetLink(email); // Send the welcome email via Resend await sendWelcomeEmail(email, link); // see below return { statusCode: 200, body: JSON.stringify({ uid: user.uid }) }; } catch (err) { return { statusCode: 500, body: JSON.stringify({ error: err.message }) }; } };
Firebase Admin SDK setup: The Admin SDK requires a service account key JSON file from Firebase. Go to Firebase Console → Project settings → Service accounts → Generate new private key. Download the JSON. In Netlify, add it as an environment variable: FIREBASE_SERVICE_ACCOUNT with the entire JSON as the value (minified, no line breaks). Add firebase-admin to your package.json dependencies and run npm install before deploying.
The welcome email

When a client's portal account is created, send them a welcome email with their login link and instructions. The password reset link Firebase generates is how they set their first password - frame it as "set up your account" rather than "reset your password."

async function sendWelcomeEmail(email, passwordSetupLink) { await fetch('https://api.resend.com/emails', { method: 'POST', headers: { 'Authorization': `Bearer ${process.env.RESEND_API_KEY}`, 'Content-Type': 'application/json' }, body: JSON.stringify({ from: process.env.FROM_EMAIL, to: email, subject: 'Your client portal is ready', html: ` <div style="font-family: Georgia, serif; max-width: 540px; margin: 0 auto;"> <h2>Your account is set up.</h2> <p>You now have access to your client portal, where you can view your invoices, session history, and shared documents.</p> <p style="margin: 28px 0;"> <a href="${passwordSetupLink}" style="background: #1e3a5f; color: white; padding: 13px 24px; text-decoration: none; border-radius: 5px; font-family: sans-serif;"> Set Up Your Password </a> </p> <p style="font-size: 13px; color: #6b7280;"> After setting your password, you can log in any time at <a href="${process.env.GUIDE_URL}/client-portal.html"> your portal </a>. This setup link expires in 24 hours. </p> </div> ` }) }); }
Uploading documents from the admin side

When you want to share a document with a client - a contract, a photo, a receipt - you upload it from the admin dashboard. The file goes to Firebase Storage and the metadata is written to the client's Firestore documents subcollection. It appears in their portal immediately.

async function uploadClientDocument(clientCode, file) { const storagePath = `clients/${clientCode}/${Date.now()}_${file.name}`; const storageRef = firebase.storage().ref(storagePath); // Upload the file const snapshot = await storageRef.put(file); // Save metadata to Firestore await db.collection('clients').doc(clientCode) .collection('documents') .add({ name: file.name, storagePath: storagePath, size: file.size, type: file.type, uploadedAt: firebase.firestore.FieldValue.serverTimestamp() }); }
File size limits: Firebase Storage on the free (Spark) plan allows up to 5GB total storage. There is no per-file limit enforced by Firebase, but set one in your upload UI: if (file.size > 10 * 1024 * 1024) { alert('File must be under 10MB'); return; }. Large files cause slow uploads with no progress feedback, which looks like the form is broken.
Disabling a client's portal access

If a client relationship ends, you can disable their portal access without deleting their data. Firebase Authentication lets you disable an account - they cannot sign in, but their Firestore documents and Storage files remain intact.

// In your admin dashboard - disable portal access async function disableClientPortal(clientCode) { const clientDoc = await db.collection('clients').doc(clientCode).get(); const uid = clientDoc.data().uid; if (!uid) { alert('This client does not have a portal account.'); return; } // Call a Netlify Function that uses Admin SDK to disable the account await fetch('/.netlify/functions/disable-client-auth', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ uid }) }); // Mark as disabled in Firestore await db.collection('clients').doc(clientCode) .update({ portalDisabled: true }); alert('Portal access disabled. The client cannot sign in.'); }
Common Issues - Admin Integration
"Cannot find module firebase-admin" when deploying the Netlify Function
The firebase-admin package must be listed in a package.json at the root of your project. Create one if it does not exist: npm init -y, then npm install firebase-admin. Netlify reads package.json and installs dependencies automatically during the build. Make sure your netlify.toml has node_bundler = "nft".
FIREBASE_SERVICE_ACCOUNT environment variable causes a JSON parse error
When pasting the service account JSON into Netlify's environment variable field, it must be on a single line with no line breaks. Use a minifier or run cat serviceAccount.json | python3 -m json.tool --compact to collapse it. Line breaks inside the JSON value will cause a parse failure when the function reads it with JSON.parse(process.env.FIREBASE_SERVICE_ACCOUNT).
Welcome email password setup link expires before the client uses it
Firebase password reset links expire after one hour by default. You can set a custom expiry duration using the Admin SDK: pass an ActionCodeSettings object to generatePasswordResetLink() with a longer expiresIn. Alternatively, note in the welcome email that the link is time-limited and include a clear instruction for what to do if it expires (go to the login page and click "Forgot password").
