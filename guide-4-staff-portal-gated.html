Module 01

Staff / Internal Portal

The staff portal is a separate, password-protected HTML page built for you and your team - not clients. It's optimized for use on a phone in the field: fast, minimal, displaying client details, service history, and notes without any page reloads. It connects to Firebase Firestore for real-time data.

Why Firebase for the portal?

The portal uses Firebase Firestore rather than Supabase for one specific reason: Firestore's real-time listeners. When you update a client's record from the admin dashboard, the portal on someone's phone in the field updates instantly without a page refresh. For a service team that needs current information, this matters.

Supabase (Modules 3-6)
Best for structured data, complex queries, and scheduled operations. Polling-based - you request data when you need it.
Firebase Firestore (Modules 8-9)
Best for app-like features with live data. Push-based - data appears on screen automatically the moment it changes.
Firebase project setup
Go to console.firebase.google.com. Sign in with a Google account and click "Add project." Name it (your business name), disable Google Analytics (not needed), and create the project.
Inside the project, click the web icon (</>) to add a web app. Give it a nickname. Disable Firebase Hosting (you're using Netlify). Click "Register app."
Firebase shows you a config object. Create portal/js/firebase-config.js in your project and paste the entire config into it. This file will be loaded by both the staff portal and the admin dashboard.
// portal/js/firebase-config.js const firebaseConfig = { apiKey: "your-api-key", authDomain: "your-project.firebaseapp.com", projectId: "your-project-id", storageBucket: "your-project.appspot.com", messagingSenderId: "000000000000", appId: "1:000000000000:web:abc123" }; firebase.initializeApp(firebaseConfig); const db = firebase.firestore();
In Firebase → Firestore Database, click "Create database." Start in test mode (allows all reads/writes - fine for development). Switch to production rules with proper authentication before going live.
Firebase API key in your HTML: Unlike Supabase's service_role key, the Firebase config object (including the API key) is designed to be in your frontend code. Firebase uses security rules - not API key secrecy - to control access. Your API key alone does nothing without matching security rules. That said, make sure your Firestore security rules are correctly set up before you go live with real client data.
Firestore data structure

Firestore organizes data into collections and documents rather than tables and rows. The structure for a client database:

clients/ (collection) ├── BIZ-1042 (document - the client's unique code is the document ID) │ name: "Sarah Johnson" │ email: "sarah@email.com" │ phone: "555-0192" │ service: "Deep Clean" │ address: "123 Oak Street, Norfolk VA" │ notes: "Has two dogs, prefers afternoon appointments" │ registered: true │ createdAt: [timestamp] │ lastService: [timestamp] │ │ sessions/ (subcollection) │ ├── [auto-id] (document) │ │ date: "2024-03-15" │ │ service: "Monthly Clean" │ │ notes: "Cleaned all 3 bedrooms, kitchen, 2 baths" │ │ completedBy: "Team A" │ └── ... └── ...
Using the client code as the document ID (instead of a Firebase auto-generated ID) means you can fetch a client's document directly with db.collection('clients').doc('BIZ-1042').get() without needing to run a query. Faster and simpler for the use case of clients accessing their own data.
Unique client code generation
async function generateUniqueClientCode(prefix = 'BIZ') { let code, attempts = 0; do { if (attempts++ > 10) throw new Error('Too many collision attempts'); const digits = String(Math.floor(1000 + Math.random() * 9000)); code = prefix + '-' + digits; // e.g., "BIZ-4821" const snap = await db.collection('clients').doc(code).get(); if (!snap.exists) break; // Code is available } while (true); return code; }
Deleting a client and all their data

This is a common Firestore gotcha: deleting a document does not delete its subcollections. If you delete a client document, all their session records remain as orphaned data in Firestore. You must delete subcollections manually first.

async function deleteClientCompletely(clientId) { if (!confirm(`Delete client ${clientId} and ALL their session history?\nThis cannot be undone.`)) return; try { // 1. Get all session documents const sessionsSnap = await db .collection('clients').doc(clientId) .collection('sessions').get(); // 2. Delete sessions in a single batch (more efficient than individual deletes) const batch = db.batch(); sessionsSnap.docs.forEach(doc => batch.delete(doc.ref)); await batch.commit(); // 3. Now safe to delete the parent document await db.collection('clients').doc(clientId).delete(); console.log(`Client ${clientId} and all sessions deleted.`); } catch (err) { console.error('Delete failed:', err); alert('Error deleting client. Check console for details.'); } }
Common Issues
Real-time updates work in one browser tab but not on a different device
Firestore real-time listeners (onSnapshot) only update the tab/device where they're running. Each client that opens the portal sets up its own listener. As long as the listener is active (the page is open), updates appear instantly. If the page was closed and reopened, it fetches fresh data on load.
Firebase free tier quota warnings
The Spark (free) plan allows 50,000 reads and 20,000 writes per day. Real-time listeners count reads differently - an onSnapshot listener counts one read for the initial fetch plus one for each document that changes. For a small business with a few dozen clients, you're unlikely to approach these limits. You can monitor usage in Firebase Console → Usage and billing.
AI handled all Firebase code: Firestore's API for reading, writing, querying, batching, and real-time subscriptions was written entirely by AI. The subcollection deletion requirement - that you must delete subcollections before parent documents - is a Firestore-specific behavior that AI flagged proactively when asked to write the delete function, preventing a data orphaning bug.
Module 02

Admin Dashboard

The admin dashboard is your command center - a single protected page where you can view all clients, see business stats, create invoices, manage bookings, and access internal notes. It shares the same Firebase database as the staff portal, so any client added here appears there instantly.

Dashboard layout pattern

The dashboard uses a fixed sidebar for navigation and a main content area with multiple panels. Only one panel is visible at a time - clicking a nav item swaps the visible panel using CSS classes. This gives you multi-section navigation with a single HTML file and zero page reloads.

/* CSS: panels are hidden by default, only .active is shown */ .panel { display: none; } .panel.active { display: block; } .sidebar-nav a { cursor: pointer; } .sidebar-nav a.active-nav { background: var(--accent); color: white; }
// JavaScript: show a panel and update the active nav link function showPanel(name) { // Hide all panels document.querySelectorAll('.panel') .forEach(el => el.classList.remove('active')); // Deactivate all nav links document.querySelectorAll('.sidebar-nav a') .forEach(el => el.classList.remove('active-nav')); // Activate the selected panel and link document.getElementById('panel-' + name)?.classList.add('active'); document.getElementById('nav-' + name)?.classList.add('active-nav'); } // Load the default panel on page open showPanel('overview');
Loading and displaying all clients
let allClients = []; // In-memory cache - all display functions use this array async function loadAllClients() { const snapshot = await db.collection('clients').orderBy('createdAt', 'desc').get(); allClients = snapshot.docs.map(doc => ({ id: doc.id, ...doc.data() })); renderClientTable(allClients); updateStats(allClients); } function renderClientTable(clients) { const tbody = document.querySelector('#clients-table tbody'); tbody.innerHTML = clients.map(c => ` <tr> <td><strong>${c.id}</strong></td> <td>${c.name || ' - '}</td> <td>${c.email || ' - '}</td> <td>${c.service || ' - '}</td> <td> <button onclick="openClientDetail('${c.id}')">View</button> <button onclick="deleteClientCompletely('${c.id}')">Delete</button> </td> </tr> `).join(''); } function updateStats(clients) { document.getElementById('stat-total').textContent = clients.length; document.getElementById('stat-active').textContent = clients.filter(c => c.registered).length; }
Client search

With all clients loaded into the allClients array, search is just a filter - no database queries needed:

document.getElementById('client-search').addEventListener('input', (e) => { const query = e.target.value.toLowerCase().trim(); if (!query) { renderClientTable(allClients); // Show all if search is empty return; } const filtered = allClients.filter(c => c.id?.toLowerCase().includes(query) || c.name?.toLowerCase().includes(query) || c.email?.toLowerCase().includes(query) || c.service?.toLowerCase().includes(query) ); renderClientTable(filtered); });
Notes stored in the browser

Internal notes - ideas, reminders, things to follow up on - don't need to sync across devices. Browser localStorage is simpler and faster for single-device use:

// Load notes when the page opens function loadNotes() { const stored = localStorage.getItem('admin_notes_v2'); return stored ? JSON.parse(stored) : []; } // Save notes function saveNote(text) { const notes = loadNotes(); notes.unshift({ id: Date.now(), text, created: new Date().toISOString() }); localStorage.setItem('admin_notes_v2', JSON.stringify(notes)); renderNotes(); }
localStorage is device-specific. Notes saved in Chrome on your laptop do not appear on your phone. If you need notes on multiple devices, save them to Firestore instead - it's a small change to the save/load functions. localStorage is also cleared if a user clears browser data, so don't rely on it for anything you can't afford to lose.
